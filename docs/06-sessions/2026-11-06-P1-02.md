The owner answered six questions, one at a time. Each answer below is the option the owner chose,

1. **Schema scope** (2026-10-21).
   - **Question.** "How much of the engine-spec §8.5 schema should P1-02's migrations create? Table
     names become permanent once a migration lands. Many columns come from provider contracts P1-03
     has not written yet or from Draft model specs: all eight are unapproved, and DR-D14 and DR-C9 are
     still open."
   - **Answer: "Backbone only (Recommended)".** "P1-02 creates the tables whose columns the spec
     already fixes: jobs and their edges, data versions, raw_data, ingestion_runs, artifact_manifest,
     production_pointers, snapshots, model_versions, training_runs, prediction_runs, engine_settings,
     diagnostic_events and quarantined_rows. Every NFL-data, identity, feature, context, benchmark and
     model-specific GRID-state table lands in the migration of the package that owns its contract or
     model spec, under the §8.5 names. I would record this as your ruling, with a matching edit to
     §8.5 and §9.5."
   - Recorded as **R1**.
2. **Hashing** (2026-10-21).
   - **Question.** "The §8.11 artifact protocol has to compute sha256 in Rust: on write, and again on
     read to raise StateCorrupt on a mismatch. No workspace crate can do this today, and CLAUDE.md
     requires owner approval for any new production dependency. How should P1-02 hash?"
   - **Answer: "Approve sha2 (Recommended)".** "Use RustCrypto `sha2` 0.10 (MIT OR Apache-2.0). It is
     already in Cargo.lock at 0.10.9 as a transitive dependency of sqlx-core, so nothing new is
     downloaded or audited. I would add it to [workspace.dependencies], have grid-persistence use it
     alone, and record the §14.2 justification (licence, advisories, maintenance, platforms) in the
     work-package file."
   - Recorded as **R2**.
3. **Migration policy** (2026-10-21).
   - **Question.** "§8.11 says P1-02 decides by ADR (this would be ADR-015, written as Proposed)
     whether migrations run automatically at start-up or through an explicit subcommand. A destructive
     migration is always a human gate. Which policy should the ADR propose?"
   - **Answer: "Explicit `grid migrate` (Recommended)".** "Every start-up compares the database with
     the binary's migrations. If any are pending, the engine refuses with a typed error and a distinct
     exit code until an operator runs `grid migrate`, which applies them under the process lock. A
     database that is newer than the binary, or whose checksums mismatch, is a typed failure. A
     scheduled `grid update` never changes the schema on its own."
   - Recorded as **R3**; ADR-015.
4. **Façade** (2026-10-21).
   - **Question.** "P0-03's follow-up note says 'P1-02 implements the synchronous façade traits'. But
     `EngineCommands` (13 methods) and `EngineQueries` (14) have no default methods. Most of those
     methods need stages that only P1-03 to P1-12 build, and the closed `EngineErrorCode` has no 'not
     available' value. How should P1-02 handle the façade?"
   - **Answer: "Engine struct, traits later (Recommended)".** "P1-02 builds `pipeline::Engine`, which
     owns the Tokio runtime, the SQLite pool, the process lock, the artifact store, the job runner and
     event delivery to diagnostic_events and tracing. It exposes inherent methods only for what P1-02
     delivers: open/migrate and the job ledger. Each trait impl lands once every one of its methods has
     a real stage, so no method is ever a placeholder. I would record this as a deviation from the
     P0-03 follow-up note."
   - Recorded as **R4**.
5. **Process lock** (answered after 2026-10-22).
   - **Question.** "The spec contradicts itself on the process lock. §8.11 step 3 says every start-up
     takes it, and §8.13 says it keeps two `grid update` runs from both promoting. But §9.4 and
     Appendix H say no exclusive lock may be held across a long job, and that reads, queries and
     exports stay available during a backtest or rebuild. Which lock model should P1-02 build? (Your
     ruling would be recorded together with a matching spec edit.)"
   - **Answer: "Lease-based, narrow locks (Recommended)".** "Every invocation takes a shared lock, and
     `grid migrate` alone takes it exclusively, so the schema never changes under a running process.
     `grid update` also holds a separate exclusive update lock, so two updates never overlap. Rebuilds,
     exports, evaluations and queries run alongside it. A RUNNING job counts as stale only when its
     heartbeat lease has expired, as §8.10 says, with no PID probing. After a crash its job resumes once
     the lease lapses (default 5 min). Promotion and rollback stay serialized by BEGIN IMMEDIATE plus a
     one-running-publication constraint."
   - Recorded as **R5**.
6. **Store refusals** (answered on or before 2026-11-05).
   - **Question.** "When the engine refuses to start, which exit code should it use? The cases are:
     migrations pending (or no database yet), a database newer than the binary or with a checksum
     mismatch, a missing or altered registered artifact (StateCorrupt), store I/O failures, and `grid
     migrate` finding the store in use. Today only DATABASE_FAILURE (30, documented as 'The SQLite
     store failed') comes close. The closed TerminalState and EngineErrorCode enums belong to the
     Approved grid.output 1.0 contract, so changing their meaning or adding values counts as MAJOR."
   - **Answer: "Reuse 30, clarify meaning (Recommended)".** "Every one of these cases exits 30.
     DATABASE_FAILURE is re-documented as 'the durable store (SQLite database, registered artifacts or
     store locks) failed or is not usable'. The precise cause travels in the EngineErrorCode and
     message: UnsupportedVersion when the schema is not current, StateCorrupt for integrity failures,
     Internal (re-documented as exiting with its attached terminal state when it has one) for I/O and
     a busy store. The contract goes to 1.1, recorded as your ruling that this is a clarification and
     not MAJOR. No enum grows."
   - Recorded as **R6**.
